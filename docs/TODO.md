### 八之一、`CL` 的构建号是 `48000` ✓，而颜色住在显示名里 ✓✓（2026-09-29 定 ✓）

**owner 定了 `1.0.0.48000-J1407b-FFF8E7` 这个写法 ✓ —— 量过之后它通过全部约束 ✓✓：**

| 查什么 | 结果 |
| --- | --- |
| **不安全字符**（`#` ✓ `/` ✓ 空格 ✓ `%` ✓ `&` ✓ `+` ✓ `?` ✓） | **一个都没有 ✓✓ —— 所以它既能当显示名 ✓，也能当产物文件名 ✓** |
| **单调** | **`2184 → 2221 → 2880 → 3028 → 3640 → 3939 → 44100 → 48000` ✓** |
| **三份 APK 各自的 `versionCode`** | **`1000 × ABI 偏移 ＋ 48000`** ✓ —— **量过 2184 那一轮：`3184` ✓ `4184` ✓ `6184` ✓，三份各不相同 ✓** |

### 三层各放什么 ✓（以 Flutter 文档的原话为准 ✓）

| 层 | 放什么 | 约束 |
| --- | --- | --- |
| **`pubspec.yaml` 的 `+` 后面** ✓ | **`48000`** ✓ | **必须是**整数**** ✓ —— 文档：`--build-number`「On Android it is used as `versionCode`」✓ |
| **`versionName`（给人看的）** ✓✓ | **`1.0.0.48000-J1407b-FFF8E7`** ✓ | **自由字符串 ✓** —— 文档：`--build-name`「a string used as the version number **shown to user**」✓ |

## 十三、咖啡：**秤不做，原料与咖啡单可以做**（owner 2026-09-29 定 ✓）

**owner 的原话**：「秤属于外接设备那边，不做，其余的像原料和咖啡单可以考虑做」。

**这句话把 §11.2 的期待收掉了一半，而那一半正是最容易误以为该做的一半。** `DESIGN.md` §11.2 把**蓝牙秤**列在「外设适配器」表的第一行（BLE GATT、精确称量、倒的时候实时读数、到量提示），并在末尾点明**咖啡秤（Acaia、Timemore 等）大多已开放 BLE 协议** —— 也就是说它是那张表里唯一协议已开着的。**但外设那一层整体不做**，所以这条不因为「技术上最容易」而例外。**§11.2 那张表仍然是设计记录，不是待办。**

**留下来的两句「可以考虑做」是这两件** ✓：

**① 咖啡原料** —— 指的是让咖啡类原料进那张表。已知原料表已经支持任意原料（189 种里糖浆、果汁、香料都在；酒窖的记瓶表单接收 `Ingredient`；`BottleConsumed` 引用 `bottleId` 而非酒类），**所以这件事本身不增加任何能力**。它真正要定的是**原料表要不要为咖啡单独长出一层分类**（豆子 / 烘焙度 / 磨度），而那件事和「`kind` + `family` 两层化」是同一件——189 种里 142 种未分类（见第二节）。**也就是说：先做分类，咖啡豆是它的第一批受益者，而不是反过来。**

**② 咖啡单** —— 指的是配方里出现以咖啡为底的条目（手冲、意式、以及已经在用的爱尔兰咖啡杯那条）。**这件事不需要新代码**：配方的数据结构与菜单价已经够用。它要的是**写**——一批配方、它们的原料与步骤。**而它有一个真问题值得先想清楚**：手冲的粉水比与注水节奏，在没有秤的前提下**只能靠人自己掌握**；所以配方里如果写「注水到 120 克」，那是一个**人对照自己的秤去执行的目标值**，而不是应用能核对的东西。**这条边界要写在配方界面上，不能假装应用知道。**

**判定：两件都可以做 ✓，但次序是「先分类，再配方」** —— 因为分类是前置数据工作，而配方是在它之上写内容。**而外设那一层（§11.2 整张表）继续不做，包括秤。**
