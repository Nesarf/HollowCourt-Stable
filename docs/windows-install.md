# Installing the Windows build without a dialog

Written 2026-10-06, after two rounds of installer windows appeared at the owner's screen and one of them **hung the
session** -- `msiexec` was waiting for a click while the command that started it waited for `msiexec`.

## The symptom, and why it is worse than a failed install

`msiexec /qn` is a *silent* install. **But when msiexec cannot parse its own command line it falls back to its UI**,
and the caller is left waiting on a process that is waiting on a person. So the failure presents as **"the session
stopped"** rather than as "the install failed", and every retry risks another window.

## The cause was the .bat, not `cmd` and not the quoting layer

Two attempts failed with **`EXIT=1639` — "invalid command line argument"**, and both were `.bat` files generated by a
Python heredoc. The second one set the path into a variable like this:

    set MSI=E:\Hollow Court Bundle\hollow-court-1.0.48000.msi

**Unquoted, and produced by a heredoc whose backslashes were being interpreted** -- so what `msiexec` received was not
the path anybody intended, and it answered with 1639 and a window. **The earlier note in this project blamed "`cmd`
eating quotes"; that is not what happened**, and the wrong diagnosis is worth replacing because it sends the next
person to the quoting layer instead of to the file that was written.

## What works, and it is one shape

**Write the `.bat` with explicit `
` line endings and quote every path**, then run it under a timeout so that a
dialog which does appear cannot hang the caller:

```bat
@echo off
set LOG=E:\DaShaoHuo\cache	mp\msi-diagnose.log
set MSI=E:\Hollow Court Bundle\hollow-court-1.0.48000.msi
if exist "%LOG%" del "%LOG%"
msiexec.exe /i "%MSI%" /qn /norestart /L*v "%LOG%"
echo EXITCODE=%ERRORLEVEL%
```

* **`/L*v` writes a log that can be read back**, which is the whole difference between diagnosing this and guessing.
* **`timeout 120` around the call**, because the failure mode is a hang rather than an error.
* **Generate the file with `newline=''` and joined `
`** -- a heredoc will mangle it.

Measured: `EXITCODE=0`, `DisplayVersion 1.0.48000`, and the shortcut resolves to `E:\Hollow Court Win\hollow_court.exe`
with a timestamp from that build.

## Verifying without running it

**The MSI can be read without installing it**, through the Windows Installer COM interface -- useful when what is in
doubt is the package rather than the machine:

```powershell
$i = New-Object -ComObject WindowsInstaller.Installer
$db = $i.GetType().InvokeMember('OpenDatabase','InvokeMethod',$null,$i,@($msi,0))
$view = $db.GetType().InvokeMember('OpenView','InvokeMethod',$null,$db,
  @("SELECT Property, Value FROM Property WHERE Property='ProductVersion'"))
```

**`ProductVersion` is in the Property table**, not in the summary information: summary property 3 is the product name
and 4 is the template `S.M.Y.T.`, which reads like a version and is not one.

## The other half of 2026-10-06

The same round found that **the MSI was registering `1.0.3939` while the application displayed `1.0.0.48000`** --
`hollow-court.wxs` carries `Version` as a literal and pubspec had moved without it. **Windows compares the product
version, so that is a downgrade**, not a wrong filename. `ProductCode` moved with it, as that file's own comment
requires. Both numbers are printed by `packaging/windows/build.sh` on one line, which is how it was seen -- **and a
check would be better than an echo**, which is recorded here rather than pretended away.
